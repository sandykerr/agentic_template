## Principal distinctions

1. **Current machine dependency:** an ongoing run reads approved originals and snapshots repeatedly, uses live Git worktrees/repository refs, and consumes report bytes at a defined gate. A deliberate stopped QA run additionally reads a version-1 checkpoint, exact run record, current QA request, checkpoint archive, and every frozen evidence file at its original path.
2. **Already consumed process output:** role stdout is parsed once and the report is embedded in canonical gate state; command stderr/stdout and persisted assignment files are mostly original observations afterward. This does **not** make them removable during QA: the freeze hashes every immediate `artifacts/` entry, irrespective of whether its semantic contents were already parsed.
3. **Retained historical/test observations:** many copied `*-files` records preserve old `/tmp` identities while deliberately omitting worktrees. These are audit observations, not self-contained continuation packages. Their machine readership is capture/validation tooling or later human-directed inspection, rather than a runtime automatically scanning the evidence directory.
4. **Development review records versus runtime review enforcement:** actual manually produced assessment/report/instruction/skill captures exist, but the runtime currently has no generic review-index, append-only finding-disposition, role-context packaging, selected-skill snapshot, or access-probe subsystem. These cannot be inferred from prose policy or ticket 33's requested additive implementation.

### Durable knowledge versus disposable history

The user's intended outcome separates **lasting development knowledge** (new decisions, directions, resolved ownership/invariants and useful regressions) from command noise, unnecessary run records and superseded bug reports. Operational dependency and the repository's present preservation policy are different constraints. For example, a finished historical command log outside any current/future machine dependency is not required by the runtime merely because the current development review policy asks to preserve original evidence. An approved retention policy could deliberately permit discarding that raw history after extracting its lasting decision or regression. That would be a policy change, not a technical impossibility or an automatic requirement to retain everything forever.

The extraction should identify what knowledge survives, where its authoritative durable record lives, which original-evidence claims can no longer be made after deletion, and which live/frozen/prerequisite dependencies must first be released. A past bug's enduring value may be a corrected contract and meaningful regression rather than every failed command or old report. This audit does not decide which individual bug reports/logs qualify or design that future skill. Current exact-byte QA/continuation dependencies remain hard runtime constraints until the associated continuation obligation ends or an approved implementation changes the mechanism; historical policy-only preservation can be reconsidered separately.

This report proposes classification questions only. It does not authorize deletion, reorganization, rewriting hashes, recompression of frozen evidence, new QA acceptance, or continuation.

Successful-output deletion requires a phase qualification:

- **After the output has been frozen by a QA request:** it is an actual machine dependency even when the command succeeded long ago. `_publish_request` hashes every present immediate artifact (`qa.py:312`, `107-109`); `_require_frozen` rejects absent or changed files (`qa.py:117-133`); stop/promotion and continue apply it (`qa.py:460-462`, `512-517`). Older milestone artifacts remain in accumulated evidence and prior checkpoint archives. Deletion here breaks the relevant current operation. A policy change alone cannot make the existing validator accept missing frozen files; future runtime changes or ending that continuation obligation are needed.
- **At ticket completion before the first QA freeze:** it is inaccurate to say deletion necessarily breaks subsequent continuation. The current collector hashes only files that still exist; it does not discover every expected stream path from the gate records. Successfully parsed role output is embedded in gate state (`runner.py:390-396`), and successful command authority uses recorded exit/source checks rather than re-parsing its stream (`records.py:146-147`; `runner.py:355-366`). The original paths would dangle and evidence would be lost, but this specific missing-file state need not trigger the future QA frozen validator. This is a source-based consequence, not a tested cleanup guarantee.
- **Other current consumers/contracts still matter:** later reviewers/repairs receive gates with output references, existing test observation capture explicitly reads both streams (`tests/test_dependencies.py:168-172`), and documentation promises full originals (`docs/ticket-harness/agents.md:294-300`; `docs/ticket-harness/inputs.md:254`). An intentional ticket-completion cleanup feature would need explicit current-record/reader/evidence-contract handling. No present runtime retention/release operation implements that behavior.
