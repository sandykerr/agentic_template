## Substantive assessment

The overall ownership choice is appropriate. The public seam is the standalone development CLI, with `CaptureStore` owning the feature-relative routing rules, capture lifecycle and metadata transitions. Producers receive a unique payload directory, write their originals exclusively, and return a receipt for registration. `main` performs argument dispatch and observable error reporting; callers do not have to reproduce the JSON construction or cross-ticket linking protocol. This is a useful deep module: deleting it would distribute routing, validation, identity calculation, locking and registration across every evidence producer. Its two cohesive operations do not need separate classes simply because their implementations are substantial.

I traced construction from `main` through Git checkout discovery, checkout-prefix resolution, `.scratch/<feature>` validation, issue matching and normalized ticket IDs. The existing `inputs.identifier` and `inputs.unique_object` definitions are reused appropriately: aliases such as zero-padded numeric IDs share the existing canonical ticket interpretation, and duplicate JSON keys cannot silently replace review facts. Scope matching in `_record` prevents a later allocation from silently changing an existing folder's ticket membership. There is, however, a mismatch between presence validation and truthiness routing for optional scope names, demonstrated in F1.

Allocation initializes one durable `evidence-review.json` per ticket or shared folder, creates distinct UUID destinations, persists the selected scope/protected paths in `allocation.json`, and links each relevant ticket to the shared authoritative record. The local ticket records hold references instead of copies of shared decisions. The same evidence-directory `flock` covers reading and replacing every affected artifact, including initialization, so cooperating helper processes cannot lose capture updates by writing old snapshots. Existing assessment/approval/execution arrays and unknown future fields remain in the loaded object and are preserved when capture fields change. New capture identities contain no approval fields. This is consistent with capture ownership and does not claim that appending evidence itself invalidates or grants a later review decision.

The future review writer requirement is explicit in both code and the helper contract: it must lock the same directory descriptor before modifying its namespaces. No competing review writer is introduced by this ticket. The operation may write several JSON files when linking shared evidence; it promises per-file atomicity and reports partial failure rather than claiming a multi-file transaction. Matching-scope allocation can repair missing shared references. Unique sibling temporary files, flushing/fsync before `os.replace`, cleanup in `finally`, and the documented exclusion of arbitrary crash recovery are proportionate. The new helper does not need to reuse `records.write_json` at the expense of its stronger filename/alias rules; the similar generic serialization shape alone is not a substantive duplication finding.

Registration restores its routing and protection context from the durable receipt, checks receipt/destination/folder identity, validates nonempty supplied facts, hashes regular payload bytes, and records original/derived identity separately. It does not pretend that a producer's source/activity/result text is independently true. New registrations compare previously registered file identities and refuse changed originals or changed facts for an existing capture. That owner operation is the right place for the invariant. Its idempotent-return placement, however, makes validation depend on record order: a matching earlier capture returns before later captures are checked. F2 gives the observed counterexample.

Protection was traced through `_safe`, `_within`, `_identity`, receipt reload and every save caller. Path traversal/absolute payload paths, symlink components, hard-linked mutable metadata/payloads and registration of the receipt as payload are rejected. Allocation protections persist; newly frozen paths can be added at registration. The contract correctly leaves arbitrary external-run discovery and adversarial replacement outside this development helper's guarantees. Producers remain responsible for exclusive creation and honoring their assigned directories. The helper writes metadata rather than rewriting issue/spec bodies or original payload files. Frozen-output and active-input obligations still apply to the operator; an empty `--protect` list is not a claim that an external run was inspected.

I traced the unchanged CLI and related runtime seams to check that this addition does not silently take over runtime ownership: `ticket_harness.__main__` still dispatches run/status/stop/continue separately; `runner._Run` initializes/saves/restores run records and canonical check references; `runner.protected_paths` and `records.protect` own runtime input/artifact protection; `qa.ownership`, `_require_frozen` and the checkpoint evidence paths retain the run-directory lock and exact-evidence responsibility. There is no runtime caller of `CaptureStore` or the new review JSON. These unchanged paths were inspected for their relationship to capture, not recertified as a complete cumulative architecture assessment. Runtime adoption remains separate, as the approved contract requires.

The prose responsibility is also clear. The capture skill owns placement/registration, links to existing verification and immutable-review requirements, and requires a separate allocation per reviewer. Implementation, testing and review guidance now route producers through it without duplicating those workflows' authority. The ADAPT change is within the explicit follow-up: it prefers retained Forest SSH terminals and compatible live `salloc`/`srun` shells, checks capacity/resource fit and remaining time before reuse, distinguishes SSH connectivity from reservation, preserves outputs before release, and explains lost-connection checks. Its noexec scratch note is qualified by actual host observations. It does not claim live Slurm verification.

I applied all upstream smell heuristics: Mysterious Name, Duplicated Code, Feature Envy, Data Clumps, Primitive Obsession, Repeated Switches, Shotgun Surgery, Divergent Change, Speculative Generality, Message Chains, Middle Man and Refused Bequest. Repository ownership and public-CLI requirements take precedence. The stored dictionaries serve the documented JSON interchange; there is no demonstrated need for an extra public type hierarchy, checker object, forwarding layer or strategy interface. The thin CLI dispatcher earns its role as the required process seam. I found no additional blocking structural smell, and do not recommend splitting cohesive code based on line count.

### Test coverage value, isolation and limitations

The new tests use the approved process/real-Git/filesystem/observable-JSON seam and no internal mocks. Each fixture creates its own temporary repository and issue set. The concurrent-producer case uses separate child processes and validates distinct locations, no lost registrations and preservation of review namespaces. The changed-original, changed-result, malformed metadata, reserved namespace, traversal, alias and frozen-subtree cases protect distinct decisions. The derivation/idempotence case checks retained original bytes and the same capture identity on retry. These are meaningful behavioral assertions; exact record fields/hashes are part of the observable interchange rather than arbitrary private implementation layout. Three concurrent allocating producers plus four registrations are a bounded contention test, not an unjustified concurrency matrix.

There are two material gaps. The scope tests omit empty optional names, allowing F1 despite the reserved-folder cases. The mutation test has only one capture, and the idempotence case has no corrupted later capture, allowing F2. Extend those existing scenario families with the demonstrated public-CLI regressions. A new test seam or exhaustive input matrix is unnecessary. Existing fixture setup and observation copying are suitable for this scope; no deletion or consolidation of tests is justified by this review.

## Findings

### F1 — Reject empty optional names before selecting a destination

**Full key:** `review-ticket-25/standards-01/F1`. **Classification:** blocking, P2 correctness. **Source:** `ticket_harness/evidence.py:163–184`, especially `if shared:` at line 170 and shared-link selection at line 184. **Contract:** ticket 25 requires consistent ticket/shared routing and shared references; `docs/agents/evidence-capture.md:8–14` reserves ticket folders and requires a descriptive shared destination, and the scope schema uses an explicit null for absence. The review standard requires explicit guarantees to hold for accepted values.

The presence check treats `--shared ''` as supplied, allowing two tickets, but the routing and linking branches treat it as absent. The public CLI probe ran `allocate --ticket 25 --ticket 26 --shared '' --purpose 'standards probe' --producer standards` in a fresh feature. It returned zero and created `evidence/ticket-25/evidence-review.json` with both tickets and `scope.shared = ""`; there was no ticket-26 artifact or shared reference. A subsequent ordinary `allocate --ticket 25 ...` returned one with `Incompatible evidence record`. Thus an accepted argument stores a shared scope in a reserved ticket destination and prevents that ticket's normal future capture, requiring explicit record recovery. This is not just an unhelpful diagnostic for invalid input: persistent incompatible state was written after successful validation.

Validate each supplied optional name with `_slug` before any evidence creation and consistently distinguish `None` from a supplied value during scope selection. Apply the same validation discipline to a supplied empty milestone, whose current truthiness branch also skips `_slug`. Extend the existing unsafe-scope CLI case with empty shared/milestone values and assert nonzero failure without allocated output. No change to the approved routing contract or larger redesign is needed. Evidence: [empty-shared observations](standards-probe-results.json).

### F2 — Finish original validation before returning an idempotent registration

**Full key:** `review-ticket-25/standards-01/F2`. **Classification:** blocking, P2 evidence-integrity validation. **Source:** `ticket_harness/evidence.py:301–310`, specifically the return at line 310. **Contract:** `register` promises to reject mutation of any registered originals (line 258); `docs/agents/evidence-capture.md:29–33` says registration checks previously registered captures and rejects changed/missing originals. The governing evidence policy requires preserved original captures and reliable file identities.

The matching-ID branch returns from inside the loop that checks all prior captures. With captures A then B in one artifact, changing B and retrying an identical registration of A returns success after checking only A. The probe observed exactly this through public commands: A and B were allocated and registered normally, B was changed, and retrying A returned zero with A's existing record. B's retained SHA256 remained `c9006d029a7c70e5bb536ac9156644e7d810ee5d33ae1c7756112db933bf768b`, while its actual bytes hashed to `80cdf534b493f131ab161a32bbd1b80bfe25d96718c40c06d4fadda79e63799e`. No adversarial race, receipt edit or review-namespace edit is involved. Although the helper does not itself overwrite B, its promised integrity check silently misses the mutation and its successful result depends on capture ordering.

Validate every registered original before deciding whether the new request is an identical retry, or retain the match until validation has completed. Preserve the existing refusal of changed same-ID facts and the no-duplicate behavior for valid retries. Add the two-capture/mutate-later/retry-earlier regression to the existing public CLI mutation/idempotence coverage. This is a local ordering fix within the current correct owner operation; another checker module or broader refactor is unnecessary. Evidence: [idempotent-retry observations](standards-probe-results.json).
