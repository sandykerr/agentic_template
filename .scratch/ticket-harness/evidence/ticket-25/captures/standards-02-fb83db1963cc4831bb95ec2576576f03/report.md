## Substantive assessment

The approved contract assigns deterministic placement and capture registration to Python, payload creation to individually allocated producers, and later assessment/approval/execution to separate owners. `CaptureStore` implements that division behind two operations, `allocate` and `register`, called by the standalone `python -m ticket_harness.evidence` process seam. It contains the routing, identity, locking and persistence knowledge that callers otherwise would have to repeat. This is a useful deep module: its interface gives producers substantial capability without requiring them to construct authoritative JSON or coordinate cross-ticket writes. Splitting its cohesive methods simply because they contain many steps would add coordination without establishing another responsibility.

Construction derives the Git checkout and requires the selected feature to be its `.scratch/<feature>` with an `issues` directory. Resolving the repository prefix accommodates the documented ADAPT checkout alias; symlink components inside the resulting evidence path are still rejected. `_ticket` reuses `inputs.identifier` to normalize numeric IDs and rejects missing/ambiguous issue matches. I inspected that unchanged definition and `unique_object`: duplicate JSON keys raise `GateFailure`, rather than allowing a later duplicate to replace a review fact. The existing shared helpers have an appropriate responsibility and add no new mutable state.

Allocation validates ticket selection, producer/purpose and optional scope names before entering ownership and creating output. `_record` checks the expected schema, folder and exact scope when restoring an artifact, so a later producer cannot silently change shared membership. A new artifact explicitly initializes empty capture/shared-reference/review namespaces. A shared allocation owns one authoritative shared record and appends relative references to each relevant ticket artifact, rather than copying shared decisions. A UUID gives each producer a distinct payload destination and receipt even when purpose, actor or bytes repeat. New capture entries contain no approval fields, so a preexisting decision cannot be inherited as a capture result.

All cooperating helper writers acquire the same evidence-directory descriptor `flock`. The lock includes record reads, initialization, identity checks and replacements; a second process therefore cannot read stale metadata and overwrite the first process's registration. Producers own payloads, not consolidated JSON. The helper modifies only capture metadata/shared links; it retains the existing assessment, approval and execution arrays and unknown future fields. The future review-tool obligation to acquire this same lock is explicit in both the module and helper contract. No other capture/review writer is introduced in this ticket, as the definitions/usages search confirms.

Persistence is proportionate to those promises. Receipts preserve scope, folder, destination, actor, purpose and allocation protections. Registration reloads the receipt, rejects location/ID disagreement and restores allocation protections before checking paths. `_load` rejects duplicate-key/non-object JSON. `_save` uses a unique sibling temporary file, flush/fsync, atomic replacement and final cleanup; callers hold ownership. Although `records.write_json` also serializes JSON, its existing fixed temporary-file behavior and runtime role differ. Reusing it would not preserve the capture primitive's safeguards; this similar shape does not establish harmful duplication.

Shared linking spans several artifact replacements and is not a multi-file transaction. The operation prevalidates destinations and reports filesystem failure. A subsequent allocation for the same scope reloads existing records, fills missing references idempotently and preserves captures/review namespaces. A failed allocation can leave an unregistered destination; the guidance explicitly says that such payloads remain unreviewed. It does not assert complete crash recovery or approval. This honest failure model is consistent with the bounded development helper contract.

Registration validates nonempty attributed facts, confines payload paths to the allocated destination, rejects duplicate payloads and receipt-as-payload, and hashes regular file bytes. Original/derived labels and derivation identities are explicit. The supplied source/activity/result strings remain producer statements; a digest establishes byte identity, not their truth. Under the lock, the repaired operation validates every prior capture's files before either returning an identical registration or appending a new capture. Changed same-ID facts still require a new allocation; healthy identical retries neither duplicate a capture nor refresh its historical facts. Changed/missing prior originals fail before any authoritative save. No approval invalidation mechanism is invented here: this slice supplies identities and facts for the later workflow to assess against exact content.

I traced every helper metadata write (`allocation.json`, primary review record, linked ticket records, registration append), its preceding destination validation and the `_safe`/`_within`/`_identity` paths. Traversal and absolute payload inputs, symlink components and hard-linked mutable files are rejected. Allocation protections persist; newly frozen paths must be supplied at registration. `_record` checks a protected exact review artifact before writes. Protecting an unrelated subtree leaves other ticket capture available. The helper never writes issue/spec bodies or original payloads. The documented operator obligations to declare applicable frozen inputs and keep producers within their assignments are part of this development interface; automatic discovery of external active runs and resistance to hostile concurrent path replacement are expressly excluded.
