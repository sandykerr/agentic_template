## Substantive assessment

The architectural division is sound in its main responsibilities, but two concrete failures in the new capture owner prevent a clean checkpoint. Allocation must preserve the distinction between ticket and shared scope for every accepted argument value. Registration's documented whole-artifact original-integrity check must run before every successful return, including an identical retry. The implementation currently fails both requirements. They are local repairs within the approved capture interface; neither requires a new state owner or a human choice about expanded scope.

The four recorded triggers are real at both ticket start and completion: the helper adds allocation-to-registration lifecycle state; durable receipts and review JSON; shared metadata across producers/tickets; and a new writer of the capture namespaces. This broader assessment is therefore required before integration independently of the routine two review axes. It is an early checkpoint for ticket25, not the full EC1 milestone checkpoint after tickets25–26 and not an EC1 acceptance or QA-readiness declaration.

### Capture lifecycle and the location of its invariants

The public development seam is `python -m ticket_harness.evidence`, separate from `ticket-harness run/status/stop/continue`. `main()` creates one `CaptureStore` and asks it to allocate or register. The caller supplies purpose/actor/ticket scope and source/activity/result facts; it does not select an arbitrary writable output path, patch consolidated JSON, or assert a passing runtime gate. The helper resolves an existing Git checkout and confines output to its `.scratch/<feature>/evidence` tree. Canonical numeric IDs and unique issue matching supply ticket identity without altering issue bodies.

`CaptureStore` earns its depth: path selection, canonical scope, per-feature locking, protected-destination validation, JSON compatibility, atomic persistence and idempotence reside behind two operations. Deleting it would distribute those coordination rules across every producer and later reviewer. There is no present second persistence adapter that warrants a registry or hypothetical abstraction. Keeping `_safe`, `_load`, `_save` and hashing as cohesive functions is appropriate. Reusing the runtime writer would pull the new development-only state into the run schema and its lifecycle unnecessarily; the helper's fsync/unique-temp-file JSON writer has a separate ownership context and justified behavior.

Allocation validates ticket membership and intends to distinguish one ticket from two-or-more shared tickets, optionally under a named milestone. Under the evidence-directory `flock`, it loads the authoritative folder record and all ticket link records before creating a destination. Each producer receives a UUID destination and separate receipt, so common actor/purpose values do not cause collisions. Producers are instructed to create only new payload files exclusively inside that destination. Consolidation stays helper-owned. Shared artifacts retain one copy of captures/review decisions, while each ticket receives only a feature-relative `shared_records` link; scope links back to the selected issue paths.

This invariant is defeated by empty optional names: presence validation uses `is None` while routing and `_slug` validation use truthiness. The resulting location and saved scope can disagree. F1 supplies observed counterexamples and the owner-local remedy. It is a consequential scope failure rather than a preference about argument style.

Registration restores the receipt's scope/destination/protections, checks that its ID matches its location, hashes completed regular payloads, and records size/SHA256/feature-relative paths along with the producer's declared facts. It rejects traversal, absolute payload escapes, allocation metadata as payload, duplicate payload names and incorrect original/derived argument combinations. Derived records retain source-file identities and do not replace originals. The helper cannot establish the semantic truth of a result string or that a supposed derivation is a faithful summary; those remain review responsibilities, as the skill correctly states.

Registration reloads the authoritative artifact while holding ownership and preserves review namespaces and unknown fields. Its intended original check compares current bytes with every previously registered file identity before returning success or appending a new identity. A changed result or payload for an existing capture ID is rejected rather than replacing history. However, an identical earlier capture returns inside that loop and skips later original checks. F2 shows that success depends on list order, despite the explicit whole-artifact check contract. Fixing the return placement retains the small public seam and keeps original-integrity policy in its owner.

### Writers, saved representation, restoration and partial outcomes

The permitted writers are explicit: producers create their allocated payloads; `CaptureStore` initializes and mutates capture metadata and shared references; later assessment/review/execution owners will write their separate namespaces under the same evidence-directory lock. Capture initializes `assessments`, `approvals` and `execution_results` to empty lists only for a newly absent record. Existing incompatible schema/scope/folder or non-list namespace fields fail instead of being reset. Existing decisions and unknown fields survive load/update/save. Those empty lists mean no captured review exists, not an invented successful historical result.

Each `evidence-review.json` is the authoritative durable record for its folder. Receipts identify allocations and protected roots; they are not alternative decisions. A new UUID/capture has no approval field, and existing approval entries are not copied into the new capture. This is a valid additive capture foundation. Ticket26's future guarded execution must bind any approval to exact assessed paths/identities and current conditions; capture does not pretend to implement that later decision/execution contract.

The directory lock serializes cooperating helper processes across both ticket and shared records. `_save` uses a same-directory unique temporary file, flush/fsync and atomic replacement. Record readers see complete old or new JSON rather than partially serialized output. Future review writers must use the same lock; preserving their list contents is not enough if they introduce an independent unsynchronized writer. The current code/docs state that required protocol before those writers exist, so no current competing review owner is concealed.

Allocation updates receipt, shared record and ticket references across multiple atomic files. A filesystem failure can leave an orphaned allocation or missing ticket link, with a nonzero diagnostic; it cannot be treated as a completed multi-file transaction. Same-scope retry adds missing links idempotently while retaining prior state, but creates another UUID allocation. This behavior and the absence of arbitrary crash recovery are documented. Registration hashes/validates before its one metadata replacement; validation failure leaves prior metadata intact. A failure after replacement but before caller acknowledgment is addressed by identical retry, subject to F2. Unregistered bytes are not inferred to be eligible for deletion.

The protection invariant is scoped to helper writes and declared frozen/active roots, not filesystem access control. `_safe` rejects destination symlink components, hard-linked mutable metadata/payloads and writes at/below declared roots. `_within` prevents lexical escapes; feature selection resolves the ADAPT checkout prefix before validating the fixed checkout-local output location. Allocation protections persist in the receipt and are combined with newly supplied registration protections. Validation of records/destinations occurs before metadata writes, and freezing an unrelated ticket subtree permits independent capture. Producers still have filesystem permissions to violate their instructions; detection at registration and the separately governed runtime integrity checks do not promise an OS sandbox or protection against adversarial races.

No automatic discovery of external active runs is present or claimed. Operators must supply applicable protected paths, and development capture cannot replace the authorized outside-input runtime-output workflow during a run. The new guidance explicitly says so. This maintains ADR-0002's exact-input/frozen-evidence authority rather than treating a successful registration as permission to update a frozen QA packet.

### Runtime run, attempt and QA owners remain correct

No runtime module imports the new helper or calls its writer. The only imports from existing runtime code into capture are ticket-ID/duplicate-key parsing and the failure type. Capture writes neither `run.json` nor assignments/gates/QA requests/decisions/checkpoints, and returns no runtime state transition. Its similarly shaped JSON and lock primitives therefore do not create a second owner of runtime authority.

`_Run` still owns preparation, scheduling, canonical gates, final outcomes and save points. `_Attempt` retains its canonical history dictionary and current-ticket projection through owned operations; initialization deliberately aliases the active ticket record. `_TicketExecution` preserves the fixed approved base while tracking repair starting source separately. Its scoped verification collaborator does not expose unrestricted runner state. Report parsing returns observations; the runner applies timeout/process/report/finding precedence and passes a validated human-decision observation to its actual attempt owner, rather than selecting an attempt by history position.

Persistence maintains the required identities: the run saves canonical gates, exports their references in the existing checkpoint representation, and `restore_checks()` rebinds restored verification entries to the dictionaries in `record['gates']`. Subsequent `validate_sources()` therefore invalidates the durable authoritative gate, including after continuation. Rejected ticket checks lose authority without removing historical evidence. The new development metadata never enters this registry and cannot authorize a repaired submission or mutate a gate into passing.

`MilestoneReview` still owns candidate inputs, request/hash, evidence freeze, decision observations and deliberate checkpoint lifecycle. It uses run-owned verification operations, and fresh/restored requests use the same input/source/frozen-content constraints. Stop/promotion remain distinct typed outcomes. Checkpoint restore validates saved record, archive, inputs, evidence, sources and destination refs before reopening the request. Actual approval must match the exact request and remain unconsumed before atomic ref promotion; final feature completion follows that outcome. Capture facts and later cleanup decisions cannot stand in for that QA decision.

The Git/process primitives retain their separate cohesive responsibilities: source cleanliness/trees/parents and direct-ref expected-old updates remain Git-owned; timeout cleanup and rejected evidence restoration remain process-record primitives applied by the runner. The accepted M1 source already contains the sanitized environment/canonical-reference repairs. No executable changes to these runtime files occur between that source and this checkpoint; the all-package inspection found no capture-induced breach. The runtime-agent guide's historical text still mentioning the old M1 finding as open does not demonstrate a reopened code failure; the actual accepted decision establishes its historical disposition. This report neither grants it new authority nor substitutes that sentence for inspecting the source.

### Plausible change traced through ownership

Consider adding a second independent evidence-assessment stage after ticket26's review stage. Its entry caller would request a separately allocated producer destination through the current capture CLI, preserving ticket/shared/milestone scope. The producer would write its original report only there and register the exact assessed source/activity/result and file identities. Capture would append facts; it would not write the new stage's approval.

The assessment owner would then acquire the same feature evidence-directory lock, reload the single authoritative folder artifact, and append stage-specific assessment records without rewriting capture IDs, prior reports or shared decisions. Ticket readers would follow `shared_records` rather than copy those decisions. The durable representation would need explicit stage/source/group identities within its owned namespace; adding incompatible top-level schema behavior would require coordinated migration rather than bypassing `_record` validation. On process restart, each owner would load its own namespace and preserve the others. Changed source/payload/proposal identities would invalidate the relevant assessment or approval in that later owner's checks; capture's hashes establish the mismatch, not its disposition. The capture scope F1 and order-dependent original check F2 must be corrected so that foundation behaves consistently.

If that stage were later adopted inside actual harness execution, it would be separate approved runtime work: the runner would coordinate it through scoped operations, validate exact-source gates and preserve canonical restored gate references; milestone review would freeze its finalized evidence before creating a consumable request. A development capture registration alone could not add a runtime stage, bypass bounded repair, accept a candidate, resume arbitrary interruption or promote refs. Public CLI/real-Git/filesystem/JSON tests would cover the new routing and preservation/invalidation failure decisions, with existing runtime regression gates retained. Thus change is local to real responsibilities, without exposing a bag of mutable runner records to the new reviewer.

## Findings

### F1 — Present-but-empty scope names bypass validation and poison authoritative folder scope

**Full key:** `review-EC1-capture-architecture-01/standards-01/F1`.

**Classification:** blocking. **Human decision needed:** false; rejecting invalid supplied names is within the approved capture contract.

**Location:** `ticket_harness/evidence.py:163`–`179` and `:184`–`198`; `_slug` at `:36`–`39` is bypassed by truthiness. The public options at `:331`–`333` accept empty strings.

**Requirement:** Ticket25 acceptance requires genuinely shared evidence in descriptive shared/milestone folders, links from all relevant tickets and a consistent authoritative artifact per folder. The helper contract states ticket folders are reserved and a different scope cannot silently reuse one.

**Evidence:** In `probe.json`, `allocate --ticket 25 --ticket 26 --shared ''` returns0 and allocates inside `evidence/ticket-25`, stores a two-ticket scope with `shared: ""`, and creates no ticket26 artifact/link. A subsequent ordinary single-ticket25 allocation returns1 with `Incompatible evidence record`. Similarly `--shared shared-evidence --milestone ''` returns0 in the unscoped shared folder, stores a non-null empty milestone scope, and then an ordinary unscoped allocation for that same shared name fails as incompatible. These are accepted CLI values, not hypothetical concurrent mutation.

**Consequence:** Validation and routing disagree on ownership identity. An invalid name can successfully create a wrong-scope authoritative record, omit required shared references and prevent later legitimate allocation into the affected ticket/shared folder. An empty variable in a caller can therefore leave persistent broken scope instead of a clean pre-write failure.

**Proportionate remedy:** Validate every supplied optional name with `_slug` whenever it is not `None`, before ownership/output creation, and consistently use that presence distinction for routing. Reject empty strings rather than converting a shared request into a ticket request. Cover both present-empty cases through the public CLI, asserting nonzero and no allocation/artifact mutation; retain legitimate one-ticket, shared and milestone cases. No new owner/schema or broad refactor is needed.

### F2 — Identical retry returns before validating later registered originals

**Full key:** `review-EC1-capture-architecture-01/standards-01/F2`.

**Classification:** blocking. **Human decision needed:** false; completing the documented integrity check is within the approved capture contract.

**Location:** `ticket_harness/evidence.py:301`–`310`, especially the successful return inside the prior-capture loop. `register` explicitly promises rejection of mutation of any registered originals at `:258`; `docs/agents/evidence-capture.md` describes checking previously registered captures in that artifact and rejecting changed/missing originals.

**Evidence:** `probe.py` registers capture A, then B in one ticket artifact, changes B's payload bytes, and retries A identically. The saved `retry_first` observation returns0 with A's capture record. Retrying B returns1 with `Registered original changed`; authoritative JSON remains unchanged. Source inspection explains the order dependence: registration validates A and returns immediately when its ID/content matches, never visiting B. The same gap applies when a later original is missing or replaced by a prohibited alias.

**Consequence:** The stated whole-artifact original-integrity gate is bypassed on a supported idempotent retry. Successful registration depends on capture order, while the authoritative artifact can contain a later stale file identity. This does not grant deletion authority or physically restore mutated bytes, but it defeats the helper's explicit failure guarantee used by producers and subsequent evidence review.

**Proportionate remedy:** Validate every existing capture's file identities before any successful return. Remember a matching existing capture while traversing, then return it only after all originals and matching metadata have been checked; preserve current no-overwrite/idempotence behavior. Add the public-CLI A/B mutation-and-retry regression with unchanged-record assertion. No runtime invalidation or reviewer-approval policy change is required.
