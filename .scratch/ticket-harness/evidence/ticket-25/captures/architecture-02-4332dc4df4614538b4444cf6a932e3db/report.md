### Capture owner, writers and depth

The external seam is `python -m ticket_harness.evidence`. `main()` accepts allocation/registration requests and constructs one store. The caller supplies feature, relevant ticket scope, purpose/producer and later source/activity/result facts. It receives a selected unique destination and receipt; it does not need to coordinate shared JSON field edits or choose arbitrary output paths.

`CaptureStore` is a deep module because two operations hide meaningful coordination: canonical routing, directory locking, schema/scope compatibility, protection checks, persisted allocation identity, shared references and registration integrity. Deleting this module would move that complexity into every implementation/check/review producer. Its interface includes the real ordering requirement—allocate, exclusively create payloads, register—and explicit error/partial-write/protection limitations. Those obligations are explained in one capture skill and helper contract rather than scattered new conventions. The small CLI dispatcher earns its process seam. No present interchangeable persistence adapter warrants a registry or hierarchy, and cohesive path/hash/JSON functions need no additional objects.

Permitted writers are distinct. Producers create payloads only within their assigned UUID directory and must preserve originals. The helper owns allocation receipts, capture entries and `shared_records`; future assessment/review/execution writers own their corresponding namespaces and must take the same evidence-directory lock. Operators supply active/frozen protections. The capture helper neither edits issue/spec bodies nor chooses findings, approval, retention, deletion, execution or QA outcomes. Existing arrays and unknown fields are preserved when loaded metadata is updated; only absent records initialize empty assessment/approval/execution arrays. Empty arrays mean no recorded review, not a fabricated historical pass.

Construction discovers the Git checkout, resolves the ADAPT checkout prefix and confines output to its `.scratch/<feature>/evidence`. `_ticket` uses the existing identifier normalization and unique issue-path match. Allocation rejects duplicates and inconsistent single/shared/milestone membership before output creation. The repaired presence tests also reject supplied empty names before `ownership()`. `_record` rejects incompatible schema, scope or folder rather than silently adopting another folder's authority. Ticket and shared membership therefore stay aligned with persisted scope.

Under the feature evidence-directory descriptor `flock`, allocation reads the authoritative folder record and every relevant ticket record before writing. A fresh UUID plus exclusive directory creation gives parallel producers distinct destinations. The receipt persists ID, scope, folder, destination, purpose, producer, protections and allocation time. One shared artifact owns its captures/decisions, and ticket records hold feature-relative references rather than copying decisions. Different ticket membership cannot silently reuse an existing named scope.

Registration restores the receipt, combines saved protections with newly supplied protections, verifies the receipt/location/ID relationship and reloads the authoritative record under ownership. `_within` rejects absolute/traversing escapes; `_safe` checks symlink components, hard-linked files and protected descendants; `_identity` requires regular payload files. The allocation receipt is excluded even when named as `./allocation.json`. Duplicate payload references and inconsistent original/derived arguments reject. Each file identity records path/size/SHA256. Derivation identities are facts, not a judgment that the summary is faithful or permitted to replace originals. Source/activity/result are producer-attributed nonempty statements; hashing certifies their associated bytes, not their truth.

The first prior-capture loop now validates every registered payload identity before any successful retry return or new append. The second loop handles matching IDs, rejecting changed same-ID facts and returning identical registrations without duplication. New capture IDs contain no copied approval field. Later review tools must bind decisions to exact content and conditions; capture does not implement or impersonate that future approval schema.

### Persistence, invalidation and observable partial transitions

The authoritative saved capture state is one `evidence-review.json` per ticket/shared folder. The allocation receipt is routing/protection provenance, not a second review authority. Every mutation uses the same directory lock, including initialization and shared-link updates, avoiding lost read-modify-write updates among cooperating producers. Future review writers must honor that protocol; preserving their fields alone would be insufficient if they used another lock.

`_save` creates a unique sibling temporary, serializes with nonfinite values rejected, flushes/fsyncs and atomically replaces one JSON file, with temporary cleanup in `finally`. It does not claim a multi-file transaction or arbitrary crash recovery. Shared allocation can fail after receipt/shared metadata but before all ticket links; the CLI reports nonzero, and retry of the same scope can complete missing references idempotently while allocating another UUID. An orphaned allocated payload remains unreviewed, not deletion-eligible. Registration validation failures occur before append/replacement and preserve prior authoritative bytes. Failure after replacement but before acknowledgment is handled by a healthy identical retry.

Original bytes are not physically immutable against their filesystem owner. Instead the skill requires exclusive creation/preservation, and later registration detects changed/missing originals before reporting success. Protection is explicitly operator-declared: allocation freezes persist and new freezes must be passed at registration. `_record` and destination checks reject affected writes while an unrelated frozen subtree does not disable independent capture elsewhere. The helper does not discover arbitrary external active runs or promise an OS sandbox/adversarial race defense. The guidance requires active/frozen inputs to remain outside authorized writable output; these are enforced or disclosed contract limits, not narrower assumptions used to excuse an accepted-input defect.

### Unchanged runtime owners and invariant coordination

There is no runtime import/call of the new writer. Capture imports only existing input parsers and a failure type. It writes neither `run.json`, runtime gates/assignments, QA request/decision/checkpoint nor refs. Similar JSON primitives and lock techniques do not establish shared authority between development capture and runtime execution.

Runtime preparation remains `inputs.load`'s responsibility. It validates configuration/commands, snapshots approved inputs, checks ticket graphs/completion and obtains normalized plan settings before returning a complete prepared result. `PreparedInputs.execution_config()` creates an outer mapping while deliberately retaining checked nested identities. `plans.validate` owns normalization/default insertion; callers do not mutate an unchecked plan into validity. `require_approved` subsequently detects changed source or artifact bytes.

The run owns state setup, scheduling, outcomes and canonical check persistence. Ticket initialization creates durable ticket dictionaries, unlocks eligible work and deliberately aliases the active `ticket`. `_Attempt` owns Running/Verifying/Rejected/Done history/projection observations and gate ranges; rejection closes the attempt without inventing a public Rejected ticket state. `_TicketExecution` keeps the original approved base separate from repair starting revision/source/context. Its scoped verification collaborator delegates owned checks/observations without handing ticket policy unrestricted runner state. On repair, prior ticket verification authority is removed but evidence remains; the fixed integration base and rejected source HEAD are revalidated before another assignment.

Report validation returns observations; `_Run.check` owns durable gate results and precedence among timeouts, process/report failure, blockers and validated human decisions. The actual owning attempt checks identity before receiving a human-decision handoff. Successful structure or zero exit alone cannot authorize integration. Git observations derive changed paths/submission identity independently of worker claims; reviewed candidate parents/tree and expected-old direct refs preserve exact source and caller state. Process execution brackets external commands with protection, preserves rejected bytes, restores harness-owned originals, kills process groups and records timeout/environment/integrity failures.

Canonical verification identity survives persistence: export records the existing gate/source/revision representation, and `restore_checks` rebinds decoded references to the objects in `record['gates']`. `validate_sources` then invalidates/saves those authoritative gate dictionaries, including after continuation. The new capture entries never enter this registry and cannot approve a repaired submission.

`MilestoneReview` owns the shared milestone's candidate, request/hash, evidence freeze, decision observations and deliberate checkpoint lifecycle. The run supplies scoped save/Git/check/export/invalidation operations. Candidate regression and unchanged approved/source/ref checks precede request publication. Fresh/restored requests use the same frozen-evidence constraints. Stop validates current identities and persists a version1 checkpoint plus archive; restore rejects changed run record, archive, inputs, evidence, verified sources or destination refs before reopening the same request. Exact unconsumed human approval is validated before atomic expected-old promotion, and consumption is saved after that transaction. Typed stopped/promoted outcomes prevent a clean stop from masquerading as completion. Arbitrary interrupted execution recovery remains outside the promise.

These owners preserve ADR-0001/0002: autonomous authorized development and local integration remain distinct from human acceptance of an exact milestone candidate. Capture registration and later cleanup decisions cannot resume arbitrary stopped work, satisfy a runtime gate, accept a candidate or promote it. No ADR conflict was found.
