### Preparation and its sole caller (criteria 1–2)

`inputs.load` at `inputs.py:387–510` remains the preparation owner. `PreparedInputs` at `:358–384` gives its completed results explicit names: validated settings, approved snapshots, normalized requirements, primary ID, selected IDs, completed IDs and applicable checked plan/worker settings. Those fields cover the runtime decisions that formerly traveled implicitly inside an enriched configuration tuple. The result has no separate lifecycle, registry or callback protocol.

`configuration` supplies validated defaults and the resolved repository is retained in settings; path-based raw `selected_tickets` and `plan` stay there. Derived requirements, selected/completed IDs, checked plan and workers occupy separate result fields. `execution_config()` creates a new outer mapping with the same derived keys previously inserted by `load`; it does not fill calculated fields back into settings. `runner._run:338–352`, the only loader caller found by definition/usage search, consumes that mapping and snapshots/primary without reproducing normalization, eligibility or worker rules. Projecting already prepared values into the existing run record is run initialization, rather than another preparation writer.

The loader documents that the caller must create `output/inputs`. The public path resolves config/output (`__main__.py:34`), creates a new output directory (`runner.py:310–314`) and creates the required subdirectories (`:23–29`). Repository, ticket bundle/selection and approved source paths are resolved before the corresponding separation checks. Therefore the documented public interface covers relative paths and symlink aliases through its existing canonicalization/new-directory preconditions; no scalar-only assumption is needed. Approved input bytes are read, copied to named artifacts and hashed (`inputs.py:435–446`); there is no source write in preparation. Configuration/plan normalization happens in decoded objects, leaving approved bytes separate.

Commands (including unused checks) are validated before capture; capture, duplicate-ID/metadata normalization, graph validation, completion verification and eligibility remain in their previous order and functions. No process or ref advancement moved into preparation. Failure still reaches the runner's `inputs` stage handler (`runner.py:436–453`) before baseline worktree/check creation at `:396–399`. Partial output may retain diagnostics/snapshots as the public contract permits. The result is returned only after readiness and prerequisite checks succeed.
