## Substantive architecture assessment

### Preparation and the run

`inputs.load` owns preparation as one operation: command availability, copied bytes and identities, normalized requirements, graph/completion validation, applicable plan/settings and executable selection. Its filesystem prerequisite is explicit. `PreparedInputs.execution_config` translates its fields into the existing saved mapping without callers computing derived fields into raw settings. `plans.validate` returns the checked normalized plan; `load` uses that returned plan for first membership. It owns membership, defaults and override rules together. The fact that it also normalizes its local parsed value is allowed by the contract. Pure parsing and graph calculations need no independent lifecycle owner.

`run` and `continue_run` own output creation/locking and continuation rejection around a small invocation of `_Run.execute`. `_Run` owns its full initialization, prepared-value consumption, feature/base/development observations, baseline, ticket scheduling, milestone progression and final classification. A failed baseline launches no assignment or repair. Each completed ticket returns its candidate; the run advances the integration observation and unlocks dependencies. Later milestones wait for the explicit promoted review result. Deliberate stop returns code2, and final feature completion follows all promotions. Current fail-fast behavior remains the approved implemented slice; independent-after-block progression belongs to later ticket29.

The run's shared durable dictionaries are a persistence representation whose permitted writers can be traced. The run initializes/replaces milestone groups, owns global outcome/failure and check observations; attempt/ticket operations own their projections; QA owns review fields and successful promotion projections. I found no required external sequence patching owner fields that reproduces the pre-refactor initialization defect. The concrete exception is process routing into a caller-owned Git index, F1, which occurs below those domain owners.

### Ticket cycles, attempts and checking

`_TicketExecution.execute` keeps the original approved `_base` fixed while `_start_revision`, previous source and repair context evolve from rejected work. `_Attempt` supplies explicit start/submit/candidate/complete/reject/handoff operations that coordinate canonical history and current-ticket observations. Rejected is intentionally an attempt state, not a public ticket state. Human-decision attachment checks the actual supplied owner, ticket/attempt and role-appropriate revision; checking does not pick `history[-1]`. Repairs create a new owner and preserve prior work/evidence. Integration failures, nonrepairable conditions and exhausted allowance stop through existing failure ownership.

`_TicketVerification` grants a ticket its scoped operations and observations; ticket policy cannot choose another ticket's evidence or read scheduling state through it. It is useful depth: removing it would return naming, persistence and registry coordination to ticket execution. The limited delegation here is not a speculative checker or a general forwarding-method framework.

Runner checking owns command execution, gate construction/registration, report evaluation and precedence. Environment failure stops before report handling; timed-out reports are not evaluated; invalid reports fail; validated consequential handoffs stop without ordinary repair even on nonzero exit; blocking findings fail and optional findings remain nonblocking. `agents.report` returns observations without mutating a canonical gate. Existing protection and process primitives preserve stage output, violation evidence and bounded cleanup. Long cohesive execution/check/preparation functions are not findings by themselves: their decisions are grouped and callers do not coordinate their internal field order.

### Durable evidence and canonical restoration

`_Run.export_checks` is the only representation-aware export into the existing `[gate, source, revision]` checkpoint shape. QA uses the operation. On restoration, `_Run.restore_checks` reconnects each saved gate to `record['gates']`; subsequent `validate_sources` mutates the actual durable gate and saves it. The operation uses equality lookup, but actual produced gates differ by stage/artifact/source/attempt identities; no accepted flow producing ambiguous equal gates was established. Rejecting an attempt removes its authorization entries without erasing durable rejected reports and preserves shared baseline validation.

Fresh QA's request regression entry references its canonical gate. JSON reconstruction cannot retain that identity, which is why run-owned reconstruction matters. Source invalidation raises before promotion and updates canonical evidence. F1's observed baseline becomes `passed=false`, `verification_status=invalidated`, showing that invalidation itself works; it cannot reverse a caller-index write already performed by the Git adapter.

### Milestone review and Git transactions

`MilestoneReview` owns exact feature/development/candidate inputs, request content/digest, frozen evidence, latest observed raw decision and deliberate checkpoint lifecycle. Its caller supplies paths, config/record and run-owned verification operations, then interprets the explicit outcome. Fresh candidate preparation runs regression on the actual merge, validates source/input/ref identities and publishes the request only afterward. Missing/unreadable decisions remain observable waits. New bytes become durable observations; exact fields/approval/request and consumed-request history control progression. Decoder and comparison `RecursionError` now enter rejection/waiting. Only successful ref advancement leads to consumed/promoted observations.

Stop applies current inputs/sources/request/evidence and both expected ref/worktree checks before preserving version1 checkpoint/archive/digest. Restoration validates deliberate stopped state, record/directory/version/checkpoint/archive identity, approved bytes, frozen evidence, exported source identities and both refs while the run holds exclusive directory ownership. The run invalidates stopped-checksum authority before resumed work; review reconstruction joins the same decision/stop logic. Done assignments, baseline and consumed decisions are not replayed. Earlier checkpoint archives and decisions remain in repeated-stop lineage. This is deliberate continuation, not crash recovery.

Ticket `promote` verifies the current development ref alongside the feature update. Milestone promotion prepares both updates. `_update_direct_branches` owns the transaction protocol, acquires both destination locks with no-dereference operations, validates direct-ref topology after prepare, then commits or aborts. Thus same-OID symbols installed before prepare are rejected under the held locks; ordinary Git writers cannot replace either locked destination afterward. Expected-old movements still reject. Disabling final ref hooks, unbuffered acknowledgement exchange and temporary-file stderr avoid the earlier unsafe window and pipe deadlock. Transaction cleanup remains internal; callers do not sequence locks themselves. Raw filesystem mutation bypassing Git locks remains outside that guarantee. F1 concerns an independent transport decision: `-C` does not override an inherited index routing variable.

The modules earn their interfaces without an inheritance hierarchy. Applying the deletion test, removing attempt/ticket/run/review owners would redistribute real sequencing decisions to callers. Removing pure transformations or replacing them with classes would add no responsibility. The current boundary needing correction is the process adapter's target-local Git routing, not class count or function length.

Existing repair exhaustion, failed baseline, human-decision precedence and rejection-history public cases test those decisions; a distinct newly classified failure needs a corresponding behavior case. No caller should patch attempt state or saved allowance mid-run.

**An additional independent review stage** necessarily has more cross-cutting contract work: the ticket owner adds its stage before candidate integration; assignment/report validation in `agents.py` supplies the new role's instructions/identity contract; `plans.validate` and input timeouts must explicitly accept its role settings and deadline; runner checking must classify its findings/decision handoff like the approved review categories. Artifact naming already derives from stage and ticket/attempt; gates and gate ranges already store stages rather than a fixed array position. Existing checkpoint config does not contain a new role/timeout, so supporting pre-change stopped runs requires an explicit compatible rule at the existing restoration/config boundary, not an unchecked lookup. Completed assignments should stay completed and an in-flight interrupted stage remains unsupported. Export/restore stays run-owned; invalidation must include the new gate's actual source. CLI/real-Git tests must show stage rejection/repair, exact revisions, optional behavior, human-decision stopping, artifact identity and old-checkpoint compatibility where promised. A newly approved stage is not justified by this assessment, and no registry/framework is needed merely to anticipate it.

These traces reveal where policy genuinely spans contracts and persisted compatibility. They do not establish a current shotgun-surgery finding: the current two review axes are explicit approved behavior, and the present owners keep their decisions out of entry callers and restoration consumers.
