## Affected flow and ownership

Entry: __main__.main -> runner.run / continue_run -> _run -> tickets.next_ready -> _TicketExecution.execute. `_run` selects the active ticket, passes its existing projection plus canonical attempt/gate lists and the current verified integration base. Configuration is read for ticket-specific check selection and commands; snapshots are copied/reordered for the ticket assignment exactly as before.

`_TicketExecution` privately keeps original approved base, current `_Attempt`, repair starting revision, previous source and failure/rejected-revision context. Its single execute operation coordinates fresh worktree/worker, Git capture, per-ticket checks, two fresh reviews, candidate construction/exact suite, expected-old promotion, rejection and bounded repair decisions. `_Attempt` remains the sole owner of lifecycle writes to its history record and current-ticket projection (initialization, source, submit, candidate, rejection, human decision and Done). Ticket policy only reads history and gates when constructing scoped assignments; no runner or run record is passed to it.

Runner-owned `_TicketVerification` provides four scoped operations: atomic observation, protected Git operation with runner naming/worktree destination, runner check with identified attempt owner, and approved-source/verified-source validation (retiring this ticket's evidence before repair). It privately holds the runner; it exposes neither the run record nor registry nor unrestricted runner access. This is one concrete internal capability, not an extensible checker framework or callback collection. Checking/report/timeout/finding precedence stays in `_Run.check`. Protected Git operations retain `_Run.git_operation` / records.protect; it owns baseline and ticket operation evidence and restoration on protected-input damage. The adapter adds ticket scoping/path derivation; validation couples approved-input checking with invalidation in the original order.

After successful promote, `_Attempt.complete` changes only owned in-memory observations; execute returns the exact tested/promoted revision. `_run` immediately writes integration_revision, unlocks dependents and saves the complete observation before selecting any next ticket. No external command or save splits Done from integration revision/unlock. Errors still propagate to `_run` for Blocked/outcome/failure classification; local stage observation preserves originating failure stage. Fail-fast remains the current loop/outer catch behavior.

Unchanged writers/consumers: tickets.initialize/unlock own Pending/Ready; `_run` owns active-ticket alias, integration revision, final Blocked/failure/outcome and milestone coordination; `_Attempt` owns attempt/current lifecycle. `_Run.check` exclusively appends canonical gates, registers verified checks and receives validated human decisions for the identified owner; agents.report returns observations. `_Run.reject_checks` removes ticket references and validates other evidence; `_Run.validate_sources` invalidates canonical gates. records.execute/protect/write_json own process artifacts/protection/atomic replacement. Git worktree/carry_changes/capture/candidate/promote primitives preserve source/ref operations. Agents.assignment consumes ticket-scoped snapshots, gate evidence, check selection, base and rejection context. QA checkpoint export/restoration and _Run.restore_checks retain canonical gate identity; no ticket execution is serialized, and deliberate continuation constructs a fresh execution only for later unfinished tickets. Status/logs consume existing durable JSON. Inputs loading/approved snapshots, earlier reports/checkpoints and caller Git work remain protected.

## Design rationale and limits

The cohesive execute operation deliberately retains the ordered cycle in one owner: repair decisions can inspect its fixed base, current attempt and rejected work without coordinating getters/setters across callers. Changing bounded repair policy is local to that owner; changing report/timeout precedence remains local to runner checking. The runner only selects a ticket, supplies concrete existing data, consumes a successful promoted revision and records progression. The four-operation runner capability grants the protection/check/observation effects needed by that cycle and fixes their ticket scope; it exposes no registry or run dictionary and introduces no callbacks, inheritance or configurable checker framework. Configuration/snapshot preparation remains its existing validated function contract pending ticket22; no general context/DI framework was introduced to reduce constructor argument count.

This is an implementation rationale and bounded source trace, not independent review. Passing hashes/tests prove the stated identities and observed behavior; they do not certify architecture, runtime role delivery, universal reliability or human acceptance.
