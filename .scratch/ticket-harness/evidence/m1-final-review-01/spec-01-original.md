## Substantive assessment

### Contract and entry paths

The approved spec's **Independent checks and exact revisions** requires: “leave the caller's existing work outside harness-owned worktrees untouched.” Its testing decisions preserve approved inputs, reviewer sources and unrelated caller work. The handoff explicitly authorizes a bounded repair across ordinary Git, configured processes and related routing paths while preserving intentional isolated-merge overrides. The original F1 is an actual write to the caller's index before later rejection, so preventing false integration alone would be insufficient.

The reviewed delta is the original-baseline-to-current repair across the three named files. `worktree_environment` at `records.py:22–46` creates a fresh environment dictionary, removing the repository-local Git routing/configuration names. Both ordinary `git.git` at `git.py:14–28` and interactive prepared ref transactions at `git.py:175–214` use it. `records.execute` at `records.py:159–168` uses it for configured processes and then supplies the same `TICKET_HARNESS_STAGE` value as before. This addresses the shared cause before any affected launch rather than attempting rollback after index mutation. There is no new persisted environment, lifecycle, shared mutable owner or writer.

I traced CLI run/continue into `_Run`, input command validation and completed-prerequisite ancestry through `git.git`, initial branch/baseline setup, `_TicketExecution._implement`, capture, lightweight checks, separate reviewer worktrees, candidate merge/suite and integration. All normal target Git reads/writes reach the filtered adapter. This includes `status`/`ls-files` source observations that can touch index metadata, not only `capture`'s explicit `add --all`/commit. Worktree creation and hooks inherit the selected Git environment. Caller HEAD/index/worktree are not copied into a restore buffer; the repair's protection is preventive, leaving the caller's state under its existing owner.

### Configured writers, accepted values and overrides

Filtering only `git.git` would leave the second writer family exposed. `_Run.check` is the sole caller of `records.execute`; baseline/lightweight/candidate/milestone suites and implementation/repair/Spec/Standards assignments all pass through it. Their child Git commands inherit the filtered environment and operate in the assigned cwd. The new agent and check staging cases exercise these independent paths. Command argv, stdin assignment JSON, report identities, role settings, positive deadlines, tracing/identity settings and the stage variable retain their existing semantics.

The filter removes each named local variable regardless of its value. Its protection therefore does not rely on `GIT_INDEX_FILE` being absent, relative, absolute, pointing at an empty file, or referring to the caller's default index. The same name-based removal covers foreign `GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR` and object routes. Removing `GIT_CONFIG_COUNT` disables inherited numbered configuration entries; leaving those inactive keys in the copied dictionary does not reactivate their configuration. Nonlocal configuration, identity, PATH and tracing remain intentional inherited settings. This remains trusted-command execution: a process deliberately supplying a new routing variable or choosing an arbitrary filesystem target is not made into an OS sandbox by the repair.

I inspected every production subprocess launch. The fourth launch, `require_clean_milestone_candidate` at `git.py:231–263`, intentionally strips all inherited `GIT_*` settings and explicitly supplies the target object directory plus disabled global/system/attribute configuration. It remains separate and unchanged. The helper does not overwrite its intentional `GIT_OBJECT_DIRECTORY`; the initialization/hash/object lookups surrounding it use the ordinary filtered adapter. Thus the plain merge comparison still detects source resolutions/custom driver effects instead of inheriting ticket approvals for different source.

Branch/reference aliases are not treated as harmless equal-OID values. `require_direct_branches`, ticket `promote`, milestone promotion and QA stop/restore retain their existing direct-ref checks. `_update_direct_branches` acquires prepared locks for both updates (or feature update plus development verification), validates topology while locked, and commits or aborts the transaction. I inspected the retained public tests for same-OID aliases installed after validation and rejection without partial advancement; no alias restriction newly substitutes for preservation.
