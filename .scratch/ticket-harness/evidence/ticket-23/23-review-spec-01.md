## Substantive assessment

The governing scope is the ticket's seven unchanged criteria and the spec's state/decision ownership, refactor verification, ticket lifecycle, exact revisions, QA and safe-continuation contracts. ### Complete lifecycle and prepared inputs: criterion 1

The actual entry flow is `__main__.main` → `runner.run` or `runner.continue_run` → `_Run.execute` (`__main__.py:29–34`, `runner.py:446–460`). Fresh output creation stays outside the run operation so an existing run is rejected rather than overwritten; both operations hold the unchanged exclusive directory-inode ownership context. Continue still performs `qa.restore` and captures rejection separately without rewriting prior evidence. Neither public wrapper writes configuration, protection, milestone index or lifecycle records.

`_Run.__init__` establishes the same subdirectories and initial/restored record as before. `execute` now owns input preparation, checked configuration projection, input-record setup, ticket initialization, approved-source protection, branch/base establishment, milestone progression and failure/final completion (`runner.py:23–178`). It calls `inputs.load` once and consumes `PreparedInputs.execution_config`, `snapshots` and `primary`; it does not resume the former enrichment of raw settings. `inputs.load` still returns a complete checked result after graph/eligibility/plan checks (`inputs.py:358–510`), and `plans.validate` remains the authority for normalized membership and worker settings. A change to run setup or continuation ordering now has a cohesive owner instead of requiring changes to the public wrappers. The long operation is cohesive under this contract; length by itself is not a defect.

### Fresh execution and failures: criterion 2

Initialization preserves its operational order. Config and snapshots are established before branch validation; protected relative source paths are derived before any baseline worktree operation. Integration ref format and checked-out rejection precede resolving the requested base and full integration branch commit, which must match (`runner.py:87–120`). The run creates and checks exactly one baseline outside ticket and milestone loops (`121–125`). A failed baseline throws before ticket assignment construction; no ticket repair loop can consume it.

Failure classification remains in the same exception boundary with the same stages: input/branch setup is `invalid-input`, baseline or explicit execution-environment failure is `environment`, and subsequent workflow failures are `incomplete` (`161–178`). Moving the orchestration into the owner did not alter those branches or introduce a catch that converts failure to completion.

### Check export, canonical reconstruction and invalidation: criterion 5

The unchanged `_TicketVerification` delegates only ticket-scoped checking/observations/validation. QA now calls `export_checks` and `_persist` receives finished checkpoint-shaped lists (`qa.py:81–108`, `295–303`); it no longer knows the in-memory tuples or converts their Paths. QA restore's iteration over saved triples is interpretation of the durable version-1 shape, not access to that internal registry.

Export preserves the exact former JSON values: each entry is `[gate, str(source), revision]`. It does not promise an independently mutable copy of gates, and synchronous persistence needs none. After JSON decoding has duplicated dictionaries, restoration resolves each exported gate through `record['gates']` and retains that actual dictionary. Consequently source invalidation updates the authoritative durable gate, rather than an equal detached checkpoint copy. Subsequent stop/export/JSON/restore cycles repeat that binding, so identity does not drift after a second continuation. Generated gates have distinct source/artifact/stage/ticket/attempt observations; equality lookup resolves the actual persisted observation rather than inventing a gate. The existing post-restore baseline-mutation test asserts durable `passed=False` and `verification_status=invalidated`; repeated-stop coverage checks lineage. Source tracing establishes the repeated canonical binding beyond what either individual scenario proves.
