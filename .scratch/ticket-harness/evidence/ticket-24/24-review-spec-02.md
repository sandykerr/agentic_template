## Findings

### F1 — Blocking: a development alias installed after validation still follows automatic feature integration

**Full key:** `review-ticket-24/spec-02/F1`. Continues the authority concern in **`review-ticket-24/standards-01/F1`**; that prior key cannot yet be considered fully fixed.

**Contract:** Ticket24 criterion 2 requires “Only an explicit matching, unconsumed human approval advances both expected feature/development refs to the exact regression-tested candidate.” Criterion6 retains human authority. ADR-0002 reserves development promotion for exact human acceptance; the spec's QA/promotion contract says “Do not overwrite concurrent branch movement.” Ownership review requires checking accepted aliases and permits relevant unchanged collaborators to block when they defeat the ticket's approved outcome. The contract does not exempt an ordinary concurrent Git symbolic-ref change. Suspending/resuming the owner only forces an otherwise possible scheduling interval; it adds no permission or new Git behavior.

**Source:** `tickets.py:281–287` calls `git.promote` after candidate verification. `git.py:109` validates feature then development using separate commands (`git.py:31–37`); `git.py:111–120` then updates **only feature** with `--no-deref` and expected-old OID. The development ref is not held/validated atomically with that write. The non-dereference option protects the written feature name, not other refs subsequently made symbolic to it. Later review/direct-ref checks execute after the unauthorized advancement.

**Concrete exact-source observation:** In the ordinary two-milestone temporary fixture, both destinations initially were direct at `80da8b21c10a4cfea1a848af2e5c8acc5d3c55ba`. After ticket03's candidate passed, the observer found the real `git ... for-each-ref --format=%(symref) refs/heads/dev` child, SIGSTOPped its CLI owner and waited for that child to finish (`Z`). Both refs were still at the original OID. The external operation was exactly:

```text
git symbolic-ref refs/heads/dev refs/heads/integration
```

That operation alone changed no resolved OID. After SIGCONT, the harness's automatic feature update advanced both observed tips to ticket03's tested ticket candidate **`decb3454833570f2676153a8b990c8733ee126a9`**. Ticket03 became Done. Ticket01 subsequently reached integration, rejected the now-visible symbolic development ref and left the durable outcome `incomplete` with failure `integration: Branch dev must not be symbolic`. There was **no QA request, observation or consumed decision**. Tickets02/04 remained Pending. The development ref already contained ticket03 without any human approval; the later rejection did not restore it. [Own retained audit](24-review-spec-02-audit.json) contains these observations and process/cleanup limits.

**Consequence:** Separate validation and non-dereferencing feature writes do not preserve the declared separation of automatic feature integration from human-controlled development advancement across a concurrent development alias replacement. This is a concrete residual form of the original blocking authority defect, despite successful repair of static aliases. It is not a claim that all concurrent same-OID symbols, every Git environment or every non-dereference operation is unsafe.

**Proportionate remedy:** Preserve destination separation at the automatic feature write itself, coordinating development's reference topology with the feature update through an effective atomic/locked check; retain expected-old commit checks and no-dereference writes. Another unlocked precheck/postcheck cannot prevent the demonstrated advancement. Keep this an in-scope Git authority repair with the existing run/ticket/review owners. Add focused public-CLI/real-Git coverage of the demonstrated interleaving without private implementation assertions, renew applicable final-source checks and whole-ticket axes. If available Git primitives require a consequential compatibility/contract change, expose that precise decision instead of treating an acknowledged race as accepted risk. No specific new class/framework or human amendment is authorized by this review.
